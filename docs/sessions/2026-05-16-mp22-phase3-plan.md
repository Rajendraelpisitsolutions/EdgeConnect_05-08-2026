## 1. Goal

Surface the reconcile outcome in the apply response and the Studio. Operators see whether the hot-reload that follows their Apply actually succeeded, was partial, or is still in flight — without polling `/diagnostics`. Close ADR-0009 work with smoke verification against the live demo gateway.

### Architectural pin (locked)

**Phase 3 is strictly observational.** `ReloadOutcomeDto` is informational only. It must never become an orchestration control surface — no retry/rollback buttons, no runtime-mutation APIs, no feedback path into reconcile sequencing. This pin protects the Phase 2 invariants from being eroded under future UX pressure.

| Q6 | Manual smoke procedure in `docs/smoke/mp22-hot-reload.md` PLUS lightweight reproducibility helpers in `scripts/smoke/` (pwsh) | CI automation is rejected (flake risk vs. signal). Helpers give reproducibility/demo/support value at near-zero cost. |

### Additional guardrails (locked at v2)

These four guardrails were not in v1 — they protect the Phase 2 runtime guarantees from being eroded by the Phase 3 observation surface.

| # | Guardrail | Why |
|---|---|---|
| K | **Outcome queue is bounded + evicting.** Capacity 64, LRU on `NewVersionId`. | Phase 3 is observational, not a durable audit store. Unbounded growth is a memory-leak vector. |
| L | **Enqueue is non-blocking and in-memory only.** No await on storage, no await on listeners, no await on UI observers. Reconcile path must not be slowed by outcome publication. | Phase 3 must not contaminate Phase 2 runtime budgets. The outcome queue uses `TaskCompletionSource` + a `Dictionary<,>` under a private lock — that's the whole surface. |
| M | **Outcome is observation, not authority.** `ReloadOutcomeDto` carries data only — no embedded actions, no callbacks, no control fields. | Prevents retry/rollback buttons and runtime-mutation APIs from sneaking in via the observation channel. See architectural pin (§1). |
| N | **Outcomes survive process lifetime only.** No durability, no replay across restart, no historical reconstruction. Process restart drops all outcomes. | Diagnostics + audit chain are the durable surfaces. The queue is a short-lived correlation buffer. |

## 4. Out of scope (explicit guardrails)

- **No new audit actions.** `Applied` + `RuntimeConfigurationFault` only. The Reload outcome lives in the apply response, not in the audit chain.
- **No auto-rollback.** Reconcile failure does not undo Apply (locked decision J).
- **No coordinator behavior change** beyond (a) enqueuing outcomes and (b) the stale-skip enqueue from Q2. The reconcile order, timeouts, fault registration are frozen at `237f536`.
- **No new diagnostics endpoint.** `/diagnostics/configuration-faults` already exists from M.P2.1 phase 3b.
- **No outcome history.** Per Q5 verdict.
- **No SignalR / push.** Operator either sees the response or polls diagnostics.
- **No durability for outcomes** (guardrail N). Outcomes are in-memory, process-lifetime only. Restart drops the queue. The audit chain + `/diagnostics/configuration-faults` are the durable surfaces.
- **No blocking publication** (guardrail L). Outcome enqueue never awaits storage / listeners / observers. Phase 2 reconcile budgets are not affected by Phase 3.
- **No control fields on `ReloadOutcomeDto`** (guardrail M, architectural pin in §1). DTO carries data only — no callbacks, no actions, no orchestration hooks. Retry/rollback must NOT be added via this surface.
- **No unbounded outcome accumulation** (guardrail K). Queue is bounded (capacity 64, LRU on `NewVersionId`).

## 8. Risks & mitigations

| Risk | Mitigation |
|---|---|
| LRU eviction races a slow ConfigApi waiter | Capacity 64 is generous; eviction only happens when 64 newer versions land. Test 6 pins the boundary. |
| Wait window holds an HTTP request thread under load | Default 10s (Q4 verdict). Configurable down via `HostOptions.ReloadOutcomeWaitMs`. Cancellation token observed; the wait is `Task.WhenAny(tcs.Task, Task.Delay(timeout, ct))` shape, NOT blocking. |
| `Reload.Status = InProgress` confuses operators | Razor banner explicitly says "see Diagnostics"; docs explain. |
| Queue + coordinator deadlock if queue ever calls back into coordinator | Queue is pure data + TCS. No callbacks. Test 4 pins multi-waiter behavior. |
| Rollback path forgotten | Phase 3 step 5 explicitly touches both endpoints. Test 17 covers Apply; add a parallel test for Rollback if scope allows. |
| bUnit absent from Management.Tests | Step 7 will check first; if absent, fall back to lighter render assertions or defer Razor tests to a follow-up. **Decision point at step 7.** |

## 10. Pause-point criteria

Stop and report if any of:

- Step 2/4/6 regression gate fails — wire-up broke an existing test.
- ConfigApi-level test reveals the wait window holds the apply mutex (it must not — `ApplyDraftAsync` returns BEFORE we wait on the queue).
- bUnit is not in Management.Tests (decide whether to add the dep or defer Razor tests).
- Smoke procedure produces a result that doesn't match the kickoff expectations (e.g. metrics rate didn't double after cadence change) — that means either Phase 2 has a bug or the kickoff expectation was wrong; either way, pause.
- An implementation decision conflicts with a v2-locked verdict (Q1-Q6) or guardrail (K-N) — pause and surface, do not silently relitigate.
