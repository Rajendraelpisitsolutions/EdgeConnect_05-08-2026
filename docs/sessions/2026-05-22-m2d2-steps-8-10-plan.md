## 2. The PUT endpoint design (sub-step 8.5)

This is the critical-path architectural piece — every wizard's Edit-mode Save calls it. Locking the shape now means Steps 8/9/10 don't relitigate it three times.

### 2.1 Route shape

```
PUT /api/v1/sources/{instanceId}
```

Lives in `Api/SourcesUpdateApi.cs`; same `/api/v1/sources` group as the existing GET endpoints in `SourcesApi.cs`. Separate file because update has different dependencies (`IConfigurationManager` + `ReloadOutcomeResolver`) and a different test surface.

### 2.2 Request body

```csharp
public sealed record UpdateSourceRequestDto
{
    /// <summary>Updated source config. InstanceId MUST match the route parameter.</summary>
    public required SourceInstanceConfig SourceConfig { get; init; }

    /// <summary>Version id captured at Edit hydration time (M.2d.2 §5.5).</summary>
    public required string BaseVersionId { get; init; }

    /// <summary>Actor for the audit entry. Defaults to "system" if omitted.</summary>
    public string? Actor { get; init; }
}
```

### 2.3 Response shapes per status code

| Code | Shape | When |
|---|---|---|
| **200 OK** | `ApplyResultDto` (same as `POST /drafts/{id}/apply`) — `{ versionId, previousVersionId, gatewayId, reload }` | Happy path: version match → draft built → validated → applied. |
| **400 Bad Request** | `{ error: string }` for body-level errors, or `ValidationResultDto` for draft validation failure | Body issues (instanceId mismatch, ProtocolName changed, etc.) or draft fails validation. |
| **404 Not Found** | `{ error: string }` | No source with the given `instanceId` in current config. |
| **409 Conflict — VERSION MISMATCH** | `ConfigVersionMismatchDto` (already exists per Step 2) | `BaseVersionId != currentManager.CurrentVersionId` at save time. |
| **409 Conflict — APPLY RACE** | `ValidationResultDto` (same as existing apply endpoint) | Draft passed validation pre-apply but failed under the apply mutex. Rare. |

**Trade-off pinned:** both 409 cases use the same status code but distinct bodies. The wizard's response handler discriminates by trying `ConfigVersionMismatchDto` deserialise first (it has three `required` properties — fails fast on the other shape).

### 2.4 Server-side flow

```
1. Parse instanceId from route.
2. Validate body.SourceConfig.InstanceId == route instanceId (else 400).
3. Load current = await mgr.GetCurrentAsync().
4. If body.BaseVersionId != mgr.CurrentVersionId → 409 ConfigVersionMismatchDto.
5. Find existing source by InstanceId in current — if missing, 404.
   (Note: BuildUpdatedSourceDraft throws ArgumentException in this case;
    we pre-check so 404 takes precedence over a 500 surfacing the throw.)
6. Try BuildUpdatedSourceDraft(current, body.SourceConfig) → newDraft.
   On ArgumentException (ProtocolName changed) → 400 with error message.
7. CreateDraftAsync(newDraft, actor) → draftId.
8. ApplyDraftAsync(draftId, actor):
   - Success → ResolveAsync for reload outcome → 200 ApplyResultDto.
   - Failure (revalidation under apply mutex) → 409 ValidationResultDto.
```

The validate step is NOT a separate API round-trip — it happens implicitly inside `ApplyDraftAsync`. Matches the locked behaviour of the existing apply endpoint.

### 2.5 Route preservation invariant assertion

The endpoint is a **thin shim** over `BuildUpdatedSourceDraft`. The byte-identical-routes invariant from Step 2 (`BuildUpdatedSourceDraft_PreservesRoutesByteIdentical`) carries through — the endpoint adds no new route-mutating code path. One endpoint-level test pins this end-to-end as a defence-in-depth check (see §2.6 test 5).

### 2.6 Endpoint test plan (5 tests)

All in `tests/ElpisEdgeConnect.Management.Tests/Api/SourcesUpdateApiTests.cs`, using the existing `WebApplicationFactory`-style fixture pattern from `ConfigApiTests` / `SourcesApiTests`.

| # | Name | Asserts |
|---|---|---|
| 1 | `Put_HappyPath_AppliesDraftAndReturnsApplyResult` | 200 OK + `ApplyResultDto.VersionId` ≠ baseline + reload outcome populated. |
| 2 | `Put_StaleBaseVersionId_Returns409VersionMismatch` | Pre-mutate config in another flow → save with the old `BaseVersionId` → 409 + `ConfigVersionMismatchDto` body. |
| 3 | `Put_ProtocolNameChanged_Returns400` | Body's `SourceConfig.ProtocolName` differs from existing source's protocol → 400 from `BuildUpdatedSourceDraft`'s `ArgumentException`. |
| 4 | `Put_SourceNotFound_Returns404` | `instanceId` doesn't match any current source → 404 (precedes the BuildUpdatedSourceDraft throw). |
| 5 | `Put_RoutePreservation_RoutesAreByteIdenticalPostSave` | Existing routed source; Edit-save changes only `DeviceName`; post-apply config has identical `RouteConfig[]` references. Pins the §5.5 invariant at the HTTP layer. |

**Why exactly 5 (handoff lower bound):** these five close the locked correctness surface — happy path, the two 409s discriminated, the two preconditions (protocol immutability + existence), and route preservation. Anything beyond duplicates `BuildUpdatedSourceDraftTests` coverage with extra HTTP plumbing.

### 2.7 InstanceId mismatch between route and body

If `route.instanceId != body.SourceConfig.InstanceId`, two valid interpretations:

- **(A)** 400 — operator/wizard bug; surface loudly.
- **(B)** Use route parameter as truth, ignore body.

v1 picks **(A)** because the wizard always sends matching ids (per Step 7 hydration locking InstanceId disabled in the UI) and a mismatch indicates a programming error worth surfacing. No test #6 — covered by test #3's broader 400 branch with a `Theory`-style addition if needed.

## 3. Razor refactor strategy (Steps 8/9/10)

### 3.1 Common transformation per wizard

Each wizard goes through five mechanical changes, in order:

1. **Add two parameters** to `@code`:
   ```csharp
   [Parameter] public EditModeContext? EditMode { get; set; }
   [Parameter] public SourceInstanceConfig? HydratedConfig { get; set; }
   ```
   Default `EditMode = null` is interpreted as Add mode (matches existing behaviour). Tests pin this.

2. **Hydrate on first render** when `EditMode?.IsEdit == true && HydratedConfig is not null`:
   ```csharp
   protected override void OnParametersSet()
   {
       if (EditMode?.IsEdit == true && HydratedConfig is not null && !_hydrated)
       {
           var hydrated = WizardModel.HydrateFromExisting(HydratedConfig);
           CopyInto(_model, hydrated);  // _model is `readonly` initialised at field decl
           _hydrated = true;
           StateHasChanged();
       }
   }
   ```
   `CopyInto` mutates the existing `_model` field-by-field. Cannot reassign because of `readonly` and because Razor's `@bind` references the field. Alternative: drop the `readonly`. **Open question Q1 below.**

3. **Wrap the layout** in `WizardShell` + `WizardSection` per §6.1, replacing the existing `<MudPaper>` + numbered `<MudText>` constructs. Substantively mechanical — the existing 5-section structure (Identity / Connection / DataPoints / Wiring / etc.) is preserved 1:1.

4. **Route the Save action** through a single entry point that branches on mode:
   ```csharp
   private async Task OnSaveAsync()
   {
       if (EditMode?.IsEdit == true) await SaveEditAsync();
       else await SaveAsDraftAsync();
   }
   ```
   `SaveAsDraftAsync` is the existing flow; `SaveEditAsync` is new — see §3.2.

5. **Disable + tooltip the immutable inputs** when `EditMode?.IsEdit == true`:
   - `InstanceId` field gets `Disabled="@_isEdit"` + `HelperText="Instance id is immutable in Edit mode"` override.
   - Protocol-level identity (e.g. `ProtocolName` is not user-editable today; no UI change needed).
   - **Add/Edit-only fields:** for now, no fields are Add-only. Q-M2D2-N4 verdict was "all body fields editable" — only InstanceId + ProtocolName are immutable. If future field becomes Add-only, lands as a wizard-local concern.

### 3.2 `SaveEditAsync` shape (shared pattern)

```csharp
private async Task SaveEditAsync()
{
    if (!CanSave() || EditMode is null || EditMode.BaseVersionId is null) return;

    _busy = true;
    try
    {
        var updatedSource = _model.BuildSourceInstance();
        var body = new UpdateSourceRequestDto
        {
            SourceConfig = updatedSource,
            BaseVersionId = EditMode.BaseVersionId,
        };
        var resp = await HttpClient.PutAsJsonAsync(
            $"/api/v1/sources/{Uri.EscapeDataString(updatedSource.InstanceId)}", body);

        if (resp.StatusCode == HttpStatusCode.Conflict)
        {
            // Discriminate the two 409 cases by trying ConfigVersionMismatchDto first.
            var raw = await resp.Content.ReadAsStringAsync();
            try
            {
                var mismatch = JsonSerializer.Deserialize<ConfigVersionMismatchDto>(raw);
                if (mismatch?.CurrentVersionId is { Length: > 0 })
                {
                    _staleEditMismatch = mismatch;
                    return;
                }
            }
            catch { /* fall through to validation 409 */ }
            // Other 409: revalidation failed under apply mutex.
            Snackbar.Add($"Save rejected at apply time: {raw}", Severity.Error);
            return;
        }
        if (!resp.IsSuccessStatusCode)
        {
            var err = await resp.Content.ReadAsStringAsync();
            Snackbar.Add($"Save failed: {err}", Severity.Error);
            return;
        }

        Snackbar.Add($"Source '{updatedSource.InstanceId}' updated.", Severity.Success);
        Nav.NavigateTo($"/sources/{Uri.EscapeDataString(updatedSource.InstanceId)}");
    }
    finally { _busy = false; }
}
```

When `_staleEditMismatch is not null`, the wizard renders `StaleEditWarningBanner` (Step 5 deliverable) before the wizard sections — operator clicks Reload, which navigates back to `/sources/{id}/edit` (re-running `SourceEditRouter.LoadAsync`, capturing the fresh `BaseVersionId`).

## 5. Open design questions (review pass — answer before v2)

### Q1 — `_model` field reassignment in Hydrate path

`AddBrotherHttpSource.razor` declares `private readonly BrotherHttpSourceWizardModel _model = new();`. To hydrate, either:

- **Option A:** Drop `readonly`, reassign `_model = WizardModel.HydrateFromExisting(HydratedConfig);` in `OnParametersSet`. Razor `@bind` references update automatically because `_model` is a reference type and the binding re-reads each render.
- **Option B:** Mutate field-by-field via a `CopyInto(target, source)` helper on each model. Preserves `readonly` but adds a private mutation helper to each wizard model — small but real surface.

**Recommendation:** Option A. The `readonly` was a default-style choice, not a correctness invariant — Razor binds happily either way. Drops a custom helper.

### Q2 — Where does `_staleEditMismatch` state live?

The wizard receives a 409 → it needs to render `StaleEditWarningBanner` above the form. The banner needs `BaseVersionId`, `CurrentVersionId`, `ChangedSinceUtc`.

- **Option A:** Wizard-local state field `_staleEditMismatch: ConfigVersionMismatchDto?`, rendered as a top-of-page banner above `WizardShell`.
- **Option B:** Bubble the 409 up to `SourceEditRouter`, which owns the banner. Requires an `EventCallback<ConfigVersionMismatchDto>` parameter on each wizard.

**Recommendation:** Option A. Keeps the failure surface co-located with the action that produced it. The router doesn't need to know.

### Q3 — Wizard sequencing: parallel refactor or template-first?

Three wizards = three large files. Two strategies:

- **Template-first:** Land Brother HTTP (Step 9, smallest) end-to-end first — including the endpoint + its tests. Once that lands and is green, refactor Focas2 (Step 8) and Modbus (Step 10) using Brother as the proven template.
- **Parallel:** Refactor all three in parallel within one big commit per step.

**Recommendation:** Template-first. The first wizard refactor will surface unforeseen Blazor/Razor gotchas (the binding semantics of EditMode + HydratedConfig, the way `OnParametersSet` interacts with first-render, the 409 banner placement); landing those gotchas on the smallest wizard and rebasing the other two against the proven shape is safer than discovering the gotcha in the middle of Focas2's 748 lines.

This re-orders Steps 8 and 9 in the handoff doc's sequence. Calling it out for explicit approval.

### Q4 — Endpoint location: `SourcesApi.cs` vs new `SourcesUpdateApi.cs`?

The existing `SourcesApi.cs` is read-only (GET / and GET /{id}). Adding PUT into it expands its scope. Two options:

- **Option A:** New file `SourcesUpdateApi.cs` exposing one `MapSourcesUpdateApi` extension method, called from `Program.cs` alongside `MapSourcesApi`.
- **Option B:** Add the PUT into `SourcesApi.cs` under a new `MapWrites` section, mirroring `ConfigApi.cs`'s read+write organisation.

**Recommendation:** Option A. The existing pattern in this codebase keeps probe API files (`MqttTestConnectionApi.cs`, `BrotherHttpProbeApi.cs`, `ModbusProbeApi.cs`) per-concern, not per-resource. Source-update is its own concern (drafts → validate → apply pipeline integration); standalone file matches that pattern.

### Q5 — Should the endpoint optionally skip the draft persistence step?

Today the apply flow always persists a draft, validates, applies. For Edit-save it would be possible to:

- **Option A:** Always persist a draft (current proposed flow). Audit trail clean; every Edit lands in `/api/v1/config/drafts` momentarily then in history.
- **Option B:** Apply the updated draft directly without persistence — skip `CreateDraftAsync`. Possible if `IConfigurationManager` exposes an "apply from configuration body" path.

**Recommendation:** Option A. Persisting the draft is the audit primitive; the cost is a brief disk hit and a short-lived file in the drafts folder. The v2 §5.5 design assumed Option A. Don't shortcut.

### Q6 — What does the wizard do on 200 OK?

Currently `SaveAsDraftAsync` (Add mode) navigates to `/config?new={draftId}` so the operator sees the draft and clicks Apply. Edit-mode is different: the apply already happened. Options:

- **Option A:** Navigate to `/sources/{instanceId}` (source detail page) on success. Operator returns to where they came from.
- **Option B:** Stay on the wizard, render a "Saved successfully — version X" banner, show a Done button.

**Recommendation:** Option A. Matches the existing `Configuration / Validate / Apply` interaction — the Edit flow's success state is "back where you started, now with your change live." Snackbar covers the confirmation.

### Q7 — Reload-outcome surfacing

The endpoint returns `ApplyResultDto.Reload`, which carries the runtime-reload classification (`Hot` / `Restart` / `Cosmetic`). Today this is rendered on the Configuration page after Apply. In Edit-save:

- **Option A:** Drop the reload outcome on the floor; just navigate to `/sources/{id}` after success.
- **Option B:** Surface it as a snackbar (`"Source updated — adapter restart needed"` for `Restart`, etc.).
- **Option C:** Land Step 12's integration test today, defer surfacing to a later milestone.

**Recommendation:** Option B with the simplest possible snackbar message — three lines of code, real value to the operator. The full surfacing UX is a later concern but the bare classification is operator-visible.

## 6. Risk register

| Risk | Mitigation |
|---|---|
| **Razor first-render binding race:** `_hydrated` flag prevents re-hydrating but `OnParametersSet` fires before first render; if `_model` mutates during binding setup, fields could be stale. | Use `OnParametersSetAsync` + explicit `StateHasChanged()` after mutation. Existing wizard code already invokes `StateHasChanged` after async edits — same pattern. |
| **`BuildUpdatedSourceDraft` throws on unknown InstanceId** but endpoint pre-checks → throw should be unreachable. If the pre-check drifts, the response becomes 500 instead of 404. | Endpoint test #4 pins 404 behaviour. Drift surfaces as a test break, not a runtime surprise. |
| **`Reload` outcome surface (Q7) reveals a deeper UX gap** — operator expects to see the affected adapters listed. | v1 lands the snackbar-only surface; if the gap surfaces in smoke testing (Step 13), a follow-up chip captures the polish work. |
| **Three wizards regressing Add-mode behaviour during refactor.** | Template-first (Q3) limits blast radius; Brother HTTP's existing AddBrotherHttpSource tests stay green throughout. Each wizard refactor commits in isolation. |
| **`StateHasChanged` after `OnParametersSet` causes double-render on hydration** — visible flicker. | Acceptable in v1; if visible, drop the explicit call and rely on Razor's parameter-change re-render. |
| **Endpoint's response shape for the two 409s requires careful client discrimination.** | Documented in §2.3 + the wizard's response handler (§3.2). One test asserts each branch. |
