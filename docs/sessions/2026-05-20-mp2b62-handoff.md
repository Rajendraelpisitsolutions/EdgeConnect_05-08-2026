## 1. What landed

### §3.A — Modbus wizard tag-table cross-validation (Locked-N composition)

- New `ProjectReference` from `ElpisEdgeConnect.Management` → `ElpisEdgeConnect.Sources.ModbusTcp`. Architecturally clean: Locked rule #11 forbids protocol↔protocol references; Management→protocol is permitted and is the natural place protocol-specific wizards live.
- `ModbusSourceWizardModel.ValidateTag(ModbusTagWizardRow)` — maps the wizard row to a `ModbusTagDefinition` and delegates to the shared `ModbusTagValidator.Validate(...)`. **Zero rule duplication** — when the adapter learns a new datatype, the wizard inherits it for free.
- `AddModbusSource.razor` — per-row `Error` + `ErrorText` on the Datatype, ByteOrder, and String length cells. `CanSave()` gated on absence of any tag-row issue.

### §3.A (scope expansion, user-approved) — Tightened shared validator

- `ModbusTagValidator.Validate(...)` now rejects `ByteOrder` on `StringN` datatypes (previously silently ignored). Three callers — wizard, CSV importer, adapter startup — all inherit the strict behavior. Restores Locked-N single-source-of-truth.
- Tiny adapter behavior change: a config with `byteOrder` on a string tag, which today silently no-ops, now faults on startup. Vanishingly unlikely to affect real-world configs but **technically a breaking change** worth calling out in the PR description.

### §3.B — Studio surfaces active config path

- `HostStartup.cs` — startup banner emits `Configuration loaded from: <path> (source: env:EDGECONNECT_DATA_ROOT|default)` after the existing `Gateway identity resolved` line.
- `CurrentConfigVersionDto` — extended with optional `ConfigPath` + `Override` fields. No new endpoint; the existing `GET /api/v1/config/version` was already in scope.
- `ConfigApi.cs` — endpoint body extracted into `BuildCurrentConfigVersionDtoAsync(...)` helper with injectable env-var lookup, making it unit-testable without a WebApplicationFactory.
- `Config.razor` — monospace path caption, copy-to-clipboard `MudIconButton`, and `Override: EDGECONNECT_DATA_ROOT` chip (`Variant.Outlined`, `Color.Info`) when an env override is in effect.

### §3.B (scope decision) — `EDGECONNECT_CONFIG_DIR` left inert

The env var is read into `HostOptions.ConfigDirectory` but nothing currently consumes that field for path resolution (`ConfigurationStorageLayout` is constructed from `ResolvedDataRoot`). The Studio surfaces ONLY `EDGECONNECT_DATA_ROOT` in the Override chip. A separate follow-up chip is queued to either wire `CONFIG_DIR` through or delete the inert read — explicitly out of M.2b.6.2 scope per anti-silent-scope-expansion.

### §3.C — Modbus wizard port helper text

One-line copy change: `"Default 502"` → `"TCP port. 502 for production Modbus TCP devices; 5020 if you're using a local Modbus simulator."` Drops the "bundled test simulator" reference to a private artifact.

### v2 amendment — String datatype column in the Modbus wizard

Surfaced during smoke by the user: the wizard's `Datatypes` dropdown was missing `string` entirely, even though the adapter fully supports `stringN`, the built-in CSV templates use it (`generic-plc.csv` declares `string16`, `cnc-via-modbus-gateway.csv` declares `string8`), and §3.A had just tightened the validator for strings. **Surfaced and resolved as an explicit v2 amendment per anti-silent-scope-expansion §6**, not absorbed into the implementation PR.

Locked rules (from the user's directive 2026-05-20):
1. String length required when datatype is `string`
2. Length must be positive (`> 0`)
3. ByteOrder disabled and auto-cleared for string datatype (validator rejects it; wizard prevents the operator from reaching that invalid state)
4. Save remains disabled while length is missing/invalid
5. CSV import keeps the fixed-form aliases (`string8`, `string16`); the wizard UX is proper any-length entry

Wire-shape contract: wizard composes `"string"` + `StringLength` into `"stringN"` when emitting via `BuildSourceInstance()`. Round-trips cleanly through `ModbusTcpSourceConfiguration.FromSourceInstance`.

## 3. Pre-existing defects surfaced during smoke

Two real bugs uncovered while attempting end-to-end smoke. **Neither was introduced by M.2b.6.2**, but both are now visible and tracked. Full reproduction recipes, suspects, and acceptance criteria captured in the spawned chips and in `2026-05-20-100-cnc-deployment-readiness.md` §5.

### Bug 2 — Sink publish path silently dead (P0, release-blocker)

- **Symptom:** Route reports `Running`, source produces 3032 points, intake drops all 3032, sink degradation/recovery events both 0, `mosquitto_sub -t '#'` shows zero messages. Pre-existing buffered data (1.8 MB on disk) does not drain post-restart either, which isolates the defect from pure backpressure-controller behavior.
- **Load-bearing invariant being violated:** A route in `Running` state with a non-empty persisted buffer, a registered sink, and zero degradation/recovery events **must eventually attempt at least one publish or emit a sink fault**.
- **Likely defect class:** worker-task observability + lifecycle truthfulness — `RoutingEngine.StartRouteAsync` does `Task.Run(() => worker.RunAsync(...))` fire-and-forget and immediately transitions to `Running` regardless of whether the worker actually starts cleanly. A faulted worker leaves the route reporting `Running` indefinitely with no surface to operators.
- **Chip queued:** P0, dedicated focused session. Brother HTTP migration + bulk-provision tooling are **explicitly held until Bug 2 resolves** per user directive.

### Bug 1 — Buffer path misaligned with DataRoot (P3, non-blocking)

- **Symptom:** `DefaultRouteBufferFactory` receives `options.ConfigDirectory` but is documented to receive the data root. Buffer SQLite files land at `<dataRoot>/config/buffer/` instead of `<dataRoot>/buffer/`. Docs/blueprint/code disagree.
- **Fix:** one-line change in `CompositionRoot.cs:104` + migration shim moving the `.db + .db-shm + .db-wal` triplet from legacy to canonical path on first open after upgrade.
- **Chip queued:** P3, can land anytime post-M.2b.6.2 merge. Lower priority than Bug 2 and M.P2.3.

## 7. Memory / project-state implications

Three things worth flagging for future sessions:

1. **Anti-silent-scope-expansion discipline works.** Two real scope-expansion moments came up during M.2b.6.2 implementation (the string-byteOrder validator tightening, and the missing string datatype in the wizard). Both were surfaced explicitly, resolved with user input, and either folded into the plan (the validator tightening) or recorded as a v2 amendment (the string column). Neither was absorbed silently. This is the discipline working as designed.

2. **Smoke testing surfaced two pre-existing bugs that automated tests didn't.** 2077 unit + integration tests pass, but the end-to-end Modbus → MQTT data path is broken. **Automated tests cover code-level invariants; they don't cover the operational invariants Bug 2 violates.** Worth remembering when planning the M.2c Runtime Tap and any future test investments — the platform needs higher-level operational-behavior tests, not just more unit tests.

3. **The "platform observability gap" the kickoff already named is now concretely demonstrated.** This entire debugging session — three healthy components (source connected, sink connected, route Running) producing one broken outcome (zero data flow) — is the exact scenario M.2c (Live Tag Watch + Runtime Tap) is scoped to fix. Capture this as a motivating example for the M.2c v1 plan when that milestone kicks off.
